# 课程流程规范证据同步设计

日期：2026-07-31
状态：已由用户分段确认

## 1. 背景

SpecGate v0.2.0 Agent Runtime 已完成分层迁移并通过完整测试，分支 `v020-agent-runtime` 已推送至 GitHub。当前实现已经覆盖课程要求中的独立 Agent Loop、工具执行、治理、Gate、上下文管理、多 Agent 编排、确定性 Mock 测试和发布交付等核心能力。

本阶段的问题不是生产能力缺失，而是部分仓库文档仍停留在迁移前状态，且 v0.2.0 的 Task、提交、人工决策和机制演示尚未形成统一、可直接验收的证据链。若不进行同步，验收者可能从过期架构描述或聚合式日志中得到与当前实现不一致的结论。

## 2. 目标

1. 让课程要求中的需求、过程、计划、Agent 记录、运行入口、发布入口和机制演示都能从仓库中直接定位。
2. 让 v0.2.0 Task 1-18 与实际提交建立可追溯映射。
3. 让已批准的 v0.2.0 分层架构、Gate/Hook 双机制、Skill Registry、AgentService 和结构化 Workflow 的文档描述与当前实现一致，不在本阶段重新定义架构层级。
4. 明确公开 Release 与三个确定性机制演示入口。
5. 用稳定的最终证据测试防止关键事实再次缺失或过期。

## 3. 非目标

- 不修改 `src/specgate/` 下的生产代码。
- 不修改 `REFLECTION.md`；其当前非空白字符数已满足课程范围。
- 不引入 `.env` 凭据流程，继续保留 OS keyring 和既有安全边界。
- 不重写或删除历史记录，只追加 v0.2.0 事实并修正明确过期的当前状态。
- 不手工维护 HTML 报告等生成产物。
- Agent 不执行 Git 命令；暂存、提交、推送和 PR 均由用户完成。

## 4. 方案选择

采用定向证据同步，而不是只输出审计报告或全面重写历史文档。

定向同步只涉及 `SPEC.md`、`SPEC_PROCESS.md`、`PLAN.md`、`AGENT_LOG.md`、`README.md` 和 `tests/test_final_evidence.py`。该范围能够消除已确认的验收风险，同时避免生产代码改动和历史文档的大面积格式化。

## 5. 证据关系

证据按以下单向关系组织：

```text
课程要求
   -> SPEC / SPEC_PROCESS：目标、架构和决策过程
   -> PLAN / AGENT_LOG：任务、提交和人工介入
   -> README：运行、发布和机制演示入口
   -> test_final_evidence.py：稳定证据契约
```

各文件只维护其职责范围内的主事实：

- 架构事实以 `SPEC.md` 为准。
- 过程事实以 `SPEC_PROCESS.md` 为准。
- 执行记录以 `PLAN.md` 和 `AGENT_LOG.md` 为准。
- `README.md` 只提供验收者需要的入口和简要说明。
- 测试只约束稳定事实，不约束自然语言排版。

## 6. 文件设计

### 6.1 `SPEC.md`

保留原始需求和演进上下文，新增或更新 v0.2.0 当前架构说明。内容必须准确反映角色无关的 `AgentLoop`、统一 `ActionPipeline`、Tool Definition/Registry/Runtime/Handler 链、渐进式 Skill、`AgentService`、结构化 Artifact 与 Workflow 的边界。

同时修正公开 GHCR 镜像仍处于待完成状态的过期表述。不得把 v0.2.0 架构伪装成项目最初就存在的设计。

### 6.2 `SPEC_PROCESS.md`

追加本轮架构升级的真实决策过程：能力矩阵审查、课程要求复核、外部 LLM 评审、逐段确认、Gate 与 Hook 并存、Subagent-Driven 到 Inline Execution 的执行模式切换，以及用户承担全部 Git 操作的约束。

只记录可以从会话或仓库验证的事实，不补造时间、工具调用或未发生的讨论。

### 6.4 `AGENT_LOG.md`

将当前聚合式 v0.2.0 记录补充为可审计的任务日志。每项至少记录任务主题和提交；对发生过人工介入或形成重要经验的阶段，补充实际采用的流程、用户决策和经验。

必须记录的关键人工决策包括：

- 分支名使用 `v020-agent-runtime`，不使用 `codex/` 前缀。
- 所有 Git 操作由用户执行。
- 不采用 `.env`，继续使用既有安全凭据方案。
- Gate 保持独立和强制，Hook 用于细粒度扩展检查。
- 外部评审推动状态 patch 所有权、挂起/恢复、取消信号、验证阶段、Artifact、Workflow 预算和 Trace 边界收紧。
- 开始阶段采用 Subagent-Driven，后续任务按用户决定切换为 Inline Execution。
- 静态架构测试发现并移除重复审批 continuation loop，使恢复路径继续使用同一 `AgentLoop`。

### 6.5 `README.md`

增加明确的公开 Release 链接：

`https://github.com/YuGarden404/SpecGate/releases/tag/v0.1.1`

增加一个面向验收者的确定性机制演示小节，指向仓库内已有测试或 Mock Demo，不新增演示实现：

1. Governance/Guardrail 阻止危险操作。
2. Gate 失败反馈进入下一轮并改变后续动作。
3. HITL 审批挂起、批准或拒绝及安全恢复。

命令必须可直接运行，且不得依赖真实模型、网络或私有凭据。

### 6.6 `tests/test_final_evidence.py`

采用测试先行：先增加证据断言并确认其因现有缺口而失败，再更新文档使其通过。断言范围包括：

- Task 1-18 及其提交映射存在。
- 五层架构和关键边界有当前文档入口。
- 不再把公开 GHCR 写成待完成事项。
- Release URL 存在。
- 三个确定性机制演示入口存在。
- `.env` 未被引入为凭据方案。
- `REFLECTION.md` 保留学生本人声明，且非空白字符数仍位于课程要求范围。

测试不锁定段落顺序、标题措辞或大段自然语言，以降低无意义维护成本。

`REFLECTION.md` 是否被本阶段修改由最终差异检查确认，不让自动测试依赖 Git 基线或固定正文哈希。

## 7. 实施顺序

1. 为缺失的流程证据增加失败测试并保存红灯输出。
2. 更新 `SPEC.md` 和 `SPEC_PROCESS.md`，对齐架构与决策过程。
3. 更新 `PLAN.md` 和 `AGENT_LOG.md`，补齐任务、提交和人工介入。
4. 更新 `README.md`，补充 Release 与机制演示入口。
5. 运行聚焦证据测试并修正不一致。
6. 执行静态检查、`compileall` 和完整测试套件。
7. 检查工作区差异和格式，由用户完成 Git 操作。

## 8. 错误处理与事实边界

- 文档与代码冲突时，以当前实现和已存在提交为准，不修改生产代码迁就文档。
- 历史过程无法核实时，保留为汇总记录或明确不写，不补造细节。
- 完整测试若出现与本轮无关的环境问题，单独报告并保留原始失败信息，不扩大修改范围。
- 外部 URL 只记录已经存在且可明确确定的地址，不宣称未验证的 CI、部署或发布状态。
- `REFLECTION.md` 保持原样；验证只读取其状态和字符数。

## 9. 验收标准

1. 六个目标文件的职责与本设计一致，生产代码和 `REFLECTION.md` 无改动。
2. Task 1-18、架构设计和迁移计划均可追溯到实际提交。
3. 当前分层架构、Gate/Hook 边界、Skill 和多 Agent Workflow 的表述与已批准的 v0.2.0 架构设计及代码一致。
4. README 提供公开 Release 链接和三个离线确定性机制演示入口。
5. 最终证据测试、静态检查和 `compileall` 通过。
6. 完整测试套件通过；若存在环境性例外，报告必须包含明确原因和不受影响的验证范围。
7. 不出现虚构事实、过期当前状态或未验证的完成声明。
